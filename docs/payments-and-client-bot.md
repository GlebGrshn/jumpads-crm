# Т‑Банк и клиентский бот

## Что уже готово

В карточке сохранённого лида есть блок **Клиент и оплата**: данные участника второго бота, персональная ссылка подключения и список счетов. Менеджер создаёт тестовый счёт на указанную сумму; ссылка сохраняется в CRM и ставится в очередь клиентского бота. После подтверждения банка:

- счёт получает статус `CONFIRMED`;
- лид переходит в колонку **Оплачено**;
- у лида появляется отдельный признак **Оплачено** и сумма подтверждённых счетов;
- клиенту ставится в очередь подтверждение оплаты;
- записывается событие в истории лида.

Переход на страницу возврата из банка не означает оплату. Решение принимается по подписанному webhook либо ответу `GetState` на кнопку **Проверить в банке**. Ключи и токены никогда не передаются в браузер.

## Настройки в .env

```dotenv
# Первый бот для пошагового сбора заявок — прежний токен
TELEGRAM_BOT_TOKEN=

# Второй, отдельный бот — создать в @BotFather
CLIENT_TELEGRAM_BOT_TOKEN=
CLIENT_BOT_USERNAME=

# Подключение Т-Банка
TBANK_MODE=demo
TBANK_TERMINAL_KEY=
TBANK_PASSWORD=
APP_PUBLIC_URL=https://your-public-crm.example

# Только если на терминале требуется передача чека: заполнить оба поля
TBANK_RECEIPT_TAXATION=
TBANK_RECEIPT_TAX=
```

`CLIENT_BOT_USERNAME` — имя без `@`; позволяет сформировать персональную ссылку ещё до подключения токена. После запуска токена имя проверяется через `getMe`. Для двух ботов нужны разные токены, их очередь сообщений и смещения обновлений изолированы.

Для платежей нужен **TerminalKey и пароль терминала интернет-эквайринга**, а не произвольный OpenAPI-ключ Т‑Банка. После заполнения переменных перезапустите приложение. `.env` и `.env.*` исключены из Git и Docker-контекста.

### Два тестовых режима

- **demo** — тестовый терминал с суффиксом `DEMO`, API `https://securepay.tinkoff.ru/v2/`. Этот режим установлен по умолчанию. Если терминал не заканчивается на DEMO, приложение откажется создавать платёж.
- **sandbox** — терминал без DEMO, API `https://rest-api-test.tinkoff.ru/v2/`. Для этой среды банк требует включить IP-адреса в белый список, в том числе для открытия платёжной формы.

Боевой режим в текущей версии не реализован. Тестовые реквизиты карт берите в кабинете терминала или в документации банка. Источники: [тест-кейсы DEMO](https://developer.tbank.ru/eacq/intro/errors/test-cases), [тестовая среда](https://developer.tbank.ru/eacq/intro/errors/test).

### Публичный адрес

`APP_PUBLIC_URL` должен быть публичным HTTPS-адресом приложения без дополнительного пути. Банк отправляет уведомления на:

```text
https://your-public-crm.example/webhooks/tbank
```

Можно развернуть приложение на постоянном хостинге или использовать HTTPS-туннель к локальному серверу. Один только `http://127.0.0.1:3010` недоступен банку. В `Init` передаются NotificationURL, SuccessURL и FailURL. Callback не требует сессии CRM, но проверяет подпись, терминал, заказ, PaymentId и сумму. На обработанное уведомление возвращается ровно `200 OK` с телом `OK`.

Источники: [Init](https://developer.tbank.ru/eacq/api/init), [подпись запросов](https://developer.tbank.ru/eacq/intro/developer/token), [уведомления банка](https://developer.tbank.ru/eacq/intro/developer/notification/), [GetState](https://developer.tbank.ru/eacq/api/get-state).

### Чеки

Если терминал требует чек, задайте систему налогообложения `TBANK_RECEIPT_TAXATION` и ставку `TBANK_RECEIPT_TAX` согласно настройкам вашего терминала. Приложение не выбирает их автоматически. В форме счёта появится обязательный email для чека. Передаётся один предмет расчёта «услуга», количество 1 и точная сумма в копейках. Этот минимальный сценарий не предназначен для сложных товарных чеков и маркировки.

## Регистрация клиента и данные в CRM

Бот получает информацию только после того, как пользователь сам начал с ним взаимодействовать. Телефон, email и прочие скрытые данные Telegram не раскрывает автоматически.

При первом личном сообщении второму боту автоматически создаётся лид с источником **Клиентский бот**. Записываются Telegram user/chat ID, имя, фамилия, username, язык, доступный признак Premium и остальные поля объектов User/Chat из обновления, даты первого/последнего обращения. Сохраняются исходные метаданные входящих обновлений, включая данные нетекстовых сообщений; файлы не скачиваются. В карточке отображаются основные поля и раскрываемый блок всех доступных данных (последние 20 обновлений в интерфейсе, вся история в БД).

Кнопка **Поделиться телефоном** передаёт контакт добровольно. В профиль сохраняется только контакт, принадлежащий самому отправителю (`contact.user_id == from.id`), вместе с доступными полями контакта. Номер переносится в поле контакта лида. Текстовые сообщения также доступны менеджерам во вкладке **Мессенджер → Клиенты**.

Повторный /start или сообщение от того же Telegram ID не создаёт ещё один лид. Если клиент ранее обращался к первому боту, запись связывается по стабильному Telegram ID. Сопоставления по одному лишь имени или username нет.

Для существующего ручного лида нажмите **Подключить клиента к боту** и передайте персональную ссылку этому клиенту. Она действует 24 часа и привязывается к первому допустимому Telegram ID. Уже привязанный к другому лиду участник или другой Telegram ID первого бота не могут забрать карточку через эту ссылку. Если пользователь уже создал отдельную карточку до получения приглашения, автоматического объединения нет — это требует отдельного решения менеджера.

## Команды клиентского бота

- `/start` — подключиться и включить уведомления по заявке; показать меню.
- `/payments` — последние счета и их ссылки/статусы.
- `/subscribe` — подписаться на рассылки агентства и включить уведомления.
- `/unsubscribe` — выключить только рассылки.
- `/stop` — выключить автоматические уведомления и рассылки.

Ссылка оплаты, подтверждение и изменения этапа отправляются автоматически при включённых уведомлениях. Клиент может продолжать обычную текстовую переписку. Счёт, созданный до подключения клиента, отправится после /start через персональную ссылку.

## Напоминание о неоплате

В форме счёта по умолчанию стоит одно напоминание через 24 часа. Время можно изменить или очистить. Сервер проверяет сроки каждые 15 секунд. Напоминание формируется только для счетов `NEW`/`FORM_SHOWED`, не повторяется на каждом цикле и сохраняется при перезапуске. Если счёт оплачен до фактической отправки напоминания, очередь отменяет это сообщение. Если уведомления отключены, сообщение не отправляется.

## Рассылки

Раздел **Мессенджер → Рассылка клиентам** доступен администратору.

1. Введите текст и при необходимости выберите тег.
2. Нажмите **Посмотреть получателей**.
3. Проверьте список и подтвердите отправку отдельной кнопкой.

Аудитория — подписавшиеся через `/subscribe` клиенты, у которых включены уведомления. Архивные лиды и заблокировавшие бота исключаются. Предпросмотр действует 10 минут. Повторная отправка одного черновика не создаёт повторную рассылку. Отписка проверяется повторно перед отправкой сообщения из очереди. История показывает число отправленных, ожидающих, отменённых и недоставленных сообщений. Вложения пока не поддерживаются.

## Учёт и ограничения

- Деньги хранятся целым числом копеек. Сумма от 1 до 1 000 000 рублей на тестовый счёт.
- Один незавершённый счёт на лид. После его завершения можно создать следующий.
- Признак «Оплачено» означает наличие хотя бы одного подтверждённого счёта; оплаченная сумма — сумма таких счетов. Она не сравнивается автоматически с плановым бюджетом сделки.
- `AUTHORIZED` означает блокировку средств, а не оплату. Для данного потока в `Init` передаётся одностадийная оплата `PayType=O`; терминал должен быть настроен соответствующим образом.
- Полный возврат исключает счёт из оплаченной суммы. При частичном возврате счёт исключается из суммы полностью подтверждённых счетов и отображается как требующий сверки. Автоматического расчёта чистой суммы частичного возврата и кнопки возврата нет.
- При неоднозначном тайм-ауте `Init` заказ сохраняется как `INIT_UNKNOWN`; повторный запрос не создаёт ещё одну финансовую операцию. Проверьте OrderId в кабинете банка. Корректно подписанное уведомление банка может восстановить связь с PaymentId. Если неизвестный заказ не существует у банка, автоматической разблокировки/пересоздания в этой версии нет.
- Входящие callbacks и клиентские обновления идемпотентны. Исходящие Telegram-сообщения используют доставку с повторами: при сбое после фактической отправки, но до записи результата возможен повтор сообщения.
- Миграция сохраняет существующие лиды. Перед изменением в этом окружении создана копия `data/before-payments.sqlite`.

## Проверки

```powershell
npm test
node scripts/verify-ui.mjs
node scripts/verify-commerce-ui.mjs
```

Браузерным проверкам нужен Playwright, как описано в README. Все тесты используют изолированные БД и подменённый транспорт банка/Telegram; деньги и реальные клиентские сообщения не отправляются. Реальная оплата и доставка через второго бота пока не проверены: ключи будут добавлены пользователем позднее.

### Платёжная форма и ошибки ссылки

Проверка DEMO API 3 октября 2026 года показала, что `Init` возвращает ссылку на `https://pay.tbank-online.com/…`. Этот точный хост добавлен к разрешённым HTTPS-адресам Т-Банка. Поддомены и похожие имена автоматически не разрешаются; ссылки с логином, паролем или нестандартным портом отклоняются.

Проверенный `PaymentId` и статус сохраняются до проверки ссылки. Если ссылка отсутствует или отклонена, CRM сообщает об этом, сохраняет возможность сверить статус в банке и не создаёт дублирующий счёт. После отмены неоплаченного счёта банк может вернуть `CANCELED` с `Amount: 0`; CRM принимает это, сохраняя первоначальную сумму счёта. Для подтверждения оплаты по-прежнему требуется точное совпадение полной суммы.
